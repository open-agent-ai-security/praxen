=== LANE FIT NOTES ===
  r1: Three strains. (1) Peer agents are one component acting as both untrusted origin and outbound destination; they are parked in user_inputs, which makes the outbound edges (context->peer, messages-helper->peer) read as flowing 'backwards' into the input lane. (2) Agentverse is likewise both an ingress source (mailbox poll) and an egress sink (registration, interaction tracking); it sits in external_deploy, so the mailbox ingress edge crosses from external_deploy into client_adapters. (3) The framework has no LLM in its base runtime, so agent_core holds an orchestrator with no model for most deployments; the model/prompt slots are filled only by the experimental chat agent. asgi.py was placed in client_adapters as the API surface the caller talks to even though it is framework-internal code.
  r2: Strained in three places. (1) Peer agents are simultaneously the untrusted input origin and the outbound destination, so peer-agent-entrypoint sits in user_inputs while also receiving edges from client_adapters — the lane model has no symmetric-counterparty slot. (2) The Almanac and Agentverse sit in external_deploy as services the agent calls, but they are also an untrusted *input* origin: the resolver consumes registry-supplied endpoint URLs unvalidated, and the mailbox delivers peer envelopes, so two edges run from external_deploy back into the agent. (3) resolver and registration are runtime internals rather than agent-invoked tools; they were placed in tools_mcp because they are the capabilities the remit's tool table enumerates, but agent_core would fit the code layout equally well. Minor: the base runtime has no LLM at all, so the agent_core lane's model slot is filled only by the optional experimental ChatProtocol path, and client_adapters holds server-side ingress rather than anything the user 'talks to'.
