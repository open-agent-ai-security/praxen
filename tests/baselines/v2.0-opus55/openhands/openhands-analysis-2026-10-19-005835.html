Executive Summary
Agent Remit (as declared) · Remit v1.2
OpenHands is declared to be a self-hosted automated AI software engineer that reads and edits code, runs shell and IPython commands, and browses the web strictly inside a sandboxed runtime, acting on operator-authorized repositories and on signature-verified GitHub, GitLab, Slack, Jira and Linear events. Its authorized counterparties are operators authenticated through the deployment's identity provider, the operator-selected LLM provider, configured git hosts, and configured agent backends. Host-direct execution is permitted only by deliberate operator runtime selection, raw secrets may flow only from the server to the sandbox, and writes outside the sandbox or authorized repositories and destructive version-control operations require human approval.
Behavior Summary (as observed)
The dominant pattern is a sandbox with real isolation substance surrounded by a control plane that trusts whatever reaches it. In the shipped OSS default the REST API and the /mcp tool server accept any network caller as the operator (DefaultUserAuth on a 0.0.0.0 bind), and every conversation automatically sources the repository's .openhands/setup.sh and loads repository and organization skills as instructions inside a sandbox that already holds the user's git-provider tokens, has unrestricted egress, and runs under NeverConfirm unless the operator opts into confirmation. One poisoned repository file or issue is therefore enough to execute code with the user's credentials, exfiltrate them, and persist the payload by pushing it back — with no repository allowlist, budget ceiling, or security audit trail to stop or reveal it.
Scope of Analysis
A Python FastAPI control plane (openhands/app_server, re-exported by the deprecated openhands/server shim) that orchestrates conversations but delegates the agent loop to the external openhands-sdk / agent-server packages running in per-conversation sandboxes chosen in config.py — Docker by default, a host subprocess under RUNTIME=local|process, or a remote runtime API. The server exposes the /api/v1 REST routers, a separately mounted FastMCP server at /mcp offering PR/MR-creation tools, and sandbox-to-server webhooks authenticated by per-sandbox session keys; OSS user authentication is the no-op DefaultUserAuth. Provider tokens and custom secrets live in a local file store and are injected into sandboxes, and conversation bootstrap auto-loads repository, organization and public skills and sources the repository's .openhands/setup.sh.

What's Working Well

Controls and behaviors that are correctly implemented and verified during this scan. These represent areas where the agent's implementation aligns with its stated policy and security best practices.

Session keys bound to running, owned sandboxes

validate_session_key rejects keys for any sandbox not in RUNNING state and validate_session_key_ownership rejects keys owned by another user, so a leaked key stops working once the sandbox pauses or stops; both behaviors are covered by unit tests.

openhands/app_server/sandbox/session_auth.py:73

Unmasked user secrets require identity plus an owned live sandbox

GET /users/me?expose_secrets=true returns raw values only after the session key is validated against a RUNNING sandbox owned by the authenticated caller, exactly the two-factor requirement the remit states.

openhands/app_server/user/user_router.py:36

Short-lived JWT-scoped secret lookups for sandboxes

When a web URL is configured, provider tokens reach the sandbox as LookupSecret references carrying a JWT bound to user and provider type with a hard expiry, rather than as static values.

openhands/app_server/app_conversation/live_status_app_conversation_service.py:1198

Docker isolation is the default runtime

Unless the operator deliberately sets RUNTIME=local|process|remote, config_from_env selects the Docker sandbox service, so agent-generated code runs in a container rather than on the host.

openhands/app_server/config.py:386

Secret redaction on all application logs

SensitiveDataFilter masks environment secrets, named key patterns and API-key literals on every handler, and RedactURLParamsFilter strips sensitive query parameters such as session keys from uvicorn access logs.

openhands/app_server/utils/logger.py:248

Pinned third-party CI actions and automated dependency updates

Every third-party GitHub Action is pinned to a full commit SHA, and Dependabot raises daily pip updates for the core and enterprise packages with a 7-day cooldown against freshly published malicious releases.

.github/dependabot.yml

Remote sandbox session keys stored hashed

The remote sandbox service persists only a SHA-256 hash of each session API key, so a database read does not yield usable sandbox credentials.

openhands/app_server/sandbox/remote_sandbox_service.py:76

OWASP LLM Top 10 (2026) Coverage

Each card represents one category and shows the top 3 findings. All items in the Findings section.

LLM01 Prompt Injection
Repository-controlled setup scripts and skills run automatically inside a sandbox holding the user's git tokens, with open egress and no approval, enabling credential exfiltration and self-persisting injection.
LLM02 Sensitive Information Disclosure
Two endpoints return raw secrets on a single credential — the sandbox session key alone, or a provider-scoped JWT alone — instead of the remit's Bearer-plus-session-key pair. Provider tokens, custom secrets and the JWT master key are written to the local file store in plaintext with default file permissions. A vendor PostHog project ingest key is hardcoded in two source files and served to every OSS web client as the default telemetry destination.
LLM03 Excessive Agency
The default control plane authenticates nobody yet binds every interface, so any network peer is treated as the operator and can start code-executing conversations. No human-approval gate guards force-pushes, branch deletion, history rewrites or other writes outside the sandbox; confirmation is off by default and only LLM-judged when enabled. The MCP tool server is mounted beside the API router, so the SESSION_API_KEY hardening never applies and any caller can open PRs with stored git tokens.
LLM04 Supply Chain
Core web and agent-protocol dependencies float without upper pins and the sandbox image is resolved by mutable tag rather than digest.

The per-task budget limit exists as a setting but nothing in the control plane passes it to the agent, so no conversation halts on spend.

Maturity Scoring Rubric

Every score above is based on this scale. A score is a snapshot of observable posture — not a verdict on the people or team behind the system.

Score Label Meaning
5 Exemplary Best-in-class; automated, continuously tested, reference quality. Rarely achieved in shipping systems.
4 Strong Comprehensive controls, active management, minor gaps. Production-ready.
3 Established Documented controls consistently applied; known gaps accepted. A respectable baseline.
2 Partial Some controls exist but coverage is incomplete; key gaps remain.
1 Ad hoc Informal or inconsistent measures; relies on individual judgment.
0 Absent No evidence this category is addressed at all.
Weighting: the weighted overall above is the sum of each category's score × weight (the per-category weights are shown on each card). Zero Trust carries double weight by design; see the RAISE framework reference for the rationale.
