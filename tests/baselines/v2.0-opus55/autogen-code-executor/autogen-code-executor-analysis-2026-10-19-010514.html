Executive Summary
Agent Remit (as declared) · Remit v1.3
The remit describes the AutoGen code executor as the component that runs code blocks delivered by an authorized coder or orchestrator agent inside an isolation boundary, under human oversight, for research and prototyping use. It authorizes a Docker container backend and an Azure Container Apps dynamic-sessions backend, plus a local host executor only with explicit operator authorization in a trusted, non-production context. Every code block needs human confirmation first, sandboxed code may reach only operator-configured network destinations, and backend credentials must never appear in code files, output or logs. If the sandbox is unavailable, the executor must halt and alert rather than fall back to running on the host.
Behavior Summary (as observed)

The main pattern is that a real sandbox exists, but the default paths step around it. The Docker backend gives genuine isolation, yet create_default_code_executor() silently swaps in host execution whenever Docker is missing or fails to start. DockerJupyterServer publishes a remotely reachable kernel gateway on every host interface. The only human-confirmation gate is the caller's approval_func, which is off by default and dropped when the agent is loaded from config.

Together these mean model-generated code from any message source can run with no confirmation, on the host if Docker is down, holding a copy of the host's environment secrets, and with no audit record of what ran. Even inside the container, network egress and privileges are left at Docker defaults.

Scope of Analysis
A Python library made of the abstract `CodeExecutor` interface in `autogen_core/code_executor/_base.py` and five backends in `autogen_ext/code_executors/`: `LocalCommandLineCodeExecutor` (host subprocess), `DockerCommandLineCodeExecutor` (docker-py `containers.create` plus `exec_run`), `JupyterCodeExecutor` (host nbclient kernel), `DockerJupyterCodeExecutor` with `DockerJupyterServer` (a Jupyter kernel gateway container reached over HTTP and WebSocket), and `ACADynamicSessionsCodeExecutor` (aiohttp calls to an Azure pool endpoint with a bearer token). A factory, `create_default_code_executor()`, picks Docker and otherwise falls back to the local executor. The approval hook (`approval_func`) and the source filter live only in the context caller, `CodeExecutorAgent` in `_code_executor_agent.py`; the executors have no gate of their own and log only lifecycle events.

What's Working Well

Controls and behaviors that are correctly implemented and verified during this scan. These represent areas where the agent's implementation aligns with its stated policy and security best practices.

Docker backend fails closed

`DockerCommandLineCodeExecutor.start()` raises a RuntimeError when the Docker daemon cannot be reached instead of degrading to host execution, so a directly constructed Docker executor never runs code unsandboxed.

python/packages/autogen-ext/src/autogen_ext/code_executors/docker/_docker_code_executor.py:508

Container mounts only the working directory

The execution container bind-mounts only the work_dir at `/workspace` and never mounts the Docker daemon socket, which keeps the host filesystem and daemon out of reach of executed code by default.
