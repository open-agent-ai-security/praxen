Executive Summary
Agent Remit (as declared) · Remit v1.2
A self-hosted, single-tenant personal AI agent that runs one agent core across a CLI, a messaging gateway, a terminal UI and an Electron desktop app, with persistent memory, self-authored skills, cron automations and subagent delegation. It may use terminal, file, code-execution, web, browser, MCP, memory, skill, cron, delegation, voice, vision, image-generation and messaging-send tools, but only for the operator and callers on an operator-configured allowlist, and ingested content must always be treated as untrusted data. Destructive shell and file operations must be operator-approved in every execution context, credentials must be stripped from subprocesses and kept out of config.yaml, telemetry must be opt-in, and the desktop layer must render agent output as inert and must never install unverified runtime code.
Behavior Summary (as observed)

Hermes has real, carefully built controls, but most of them are interactive-mode heuristics that quietly turn off at the edges. The approval gate prompts in the CLI and gateway, but the -z oneshot path forces HERMES_YOLO_MODE, other non-interactive contexts auto-approve with only a log warning, and write_file/patch overwrite files with no gate at all. The agent can also switch the gate off itself, because hermes config set approvals.mode off is not a flagged command. Gateway authorization is default-deny, yet the WeCom, Weixin and QQBot adapters default to dm_policy: open and short-circuit that check.

The dominant chain runs from untrusted content to host execution and persistence. Delimiter labeling covers only web, browser and MCP tool output, nothing enforces the documented rule that untrusted surfaces need a sandboxed backend (the default is local), and injected text can be written to MEMORY.md or to unscanned agent-created skills, where it is reloaded in every later session. On the desktop side, the runtime is installed by piping a script from a mutable main branch into a shell with no integrity check.

Scope of Analysis
Two source roots: a Python agent (hermes-agent/) whose run_agent.py / agent/ loop dispatches tools registered in toolsets.py and tools/ — shell via tools/terminal_tool.py gated by the pattern-based tools/approval.py, MCP via tools/mcp_tool.py, and memory and skills via tools/memory_tool.py and tools/skill_manager_tool.py — plus a gateway (gateway/run.py, ~30 adapters in gateway/platforms/), an OpenAI-compatible API server, a FastAPI dashboard (hermes_cli/web_server.py) and the TUI JSON-RPC gateway. The Electron/TypeScript desktop app (hermes-desktop/) drives the agent over the loopback API server (src/main/hermes.ts), runs SSH tunnels and remote control (ssh-tunnel.ts, ssh-remote.ts), installs and updates the runtime by piping the upstream install.sh / install.ps1 from the main branch (src/main/installer.ts), and ships PostHog analytics in the renderer (src/renderer/src/utils/analytics.ts). The default terminal backend is the local host, and runtime state lives in ~/.hermes (config.yaml, .env, logs/, state.db, memories, skills).

What's Working Well

Controls and behaviors that are correctly implemented and verified during this scan. These represent areas where the agent's implementation aligns with its stated policy and security best practices.

API server fails closed without a key

The API server adapter refuses to start unless API_SERVER_KEY is set, even on loopback, and refuses placeholder keys on network-accessible binds. Its default host is 127.0.0.1.

hermes-agent/gateway/platforms/api_server.py:4146

Dashboard loopback, Host-header and token gates

The dashboard binds loopback by default, checks the Host header against DNS rebinding, requires a per-process session token on REST and WebSocket, and needs --insecure plus an OAuth gate for non-loopback binds.

hermes-agent/hermes_cli/web_server.py:155

Default-deny gateway authorization

_is_user_authorized denies any caller who is not on an env allowlist, a pairing list or an explicit allow-all flag, and the gateway warns at startup when no allowlists are configured.

hermes-agent/gateway/run.py:6609

Hardline command floor and cron deny default

Catastrophic commands (rm -rf /, mkfs, dd to raw devices, fork bombs, shutdown) are blocked before any yolo or mode=off bypass, and cron jobs deny dangerous commands unless the operator opts in.

hermes-agent/tools/approval.py:944

MCP subprocess environment allowlist

MCP stdio servers receive only an allowlisted set of OS variables plus their explicitly configured env, so provider and gateway credentials do not reach them by default.

hermes-agent/tools/mcp_tool.py:296

Inert agent-output rendering in the desktop renderer

Agent markdown is rendered with react-markdown and no raw-HTML plugin, under a strict CSP (script-src 'self', img-src 'self' data:), with sandboxed, context-isolated renderers and a protocol allowlist for opened links.

hermes-desktop/src/renderer/src/components/AgentMarkdown.tsx:136

Exact-pinned Python dependencies with OSV CI

Every core and lazy-installed Python dependency is pinned with == and locked in uv.lock, and osv-scanner runs on PR, push and a weekly schedule alongside a supply-chain-audit workflow and Dependabot.

hermes-agent/pyproject.toml

Security regression tests tied to fixed bypasses

Reported authorization and injection bypasses are fixed and pinned with regression tests that cite the originating issue, and those tests run in CI on every PR. This is evidence of a working feedback loop.

hermes-agent/tests/gateway/test_busy_session_auth_bypass.py:1

Contained attachment cache paths

Inbound document filenames are reduced to their basename and resolve-checked against the cache directory before any write, which closes the external-filename path-traversal pattern.

hermes-agent/gateway/platforms/base.py:1211

Webhook routes require HMAC secrets

The generic webhook adapter refuses routes without an HMAC secret and allows its INSECURE_NO_AUTH testing escape hatch only on loopback hosts.

hermes-agent/gateway/platforms/webhook.py:151

Every score above is based on this scale. A score is a snapshot of observable posture — not a verdict on the people or team behind the system.

Score Label Meaning
5 Exemplary Best-in-class; automated, continuously tested, reference quality. Rarely achieved in shipping systems.
4 Strong Comprehensive controls, active management, minor gaps. Production-ready.
3 Established Documented controls consistently applied; known gaps accepted. A respectable baseline.
2 Partial Some controls exist but coverage is incomplete; key gaps remain.
1 Ad hoc Informal or inconsistent measures; relies on individual judgment.
0 Absent No evidence this category is addressed at all.
Weighting: the weighted overall above is the sum of each category's score × weight (the per-category weights are shown on each card). Zero Trust carries double weight by design; see the RAISE framework reference for the rationale.
