Executive Summary
Agent Remit (as declared)
OpenHands is declared as a self-hosted, always-on automated AI software engineer — a developer control centre that runs coding agents to read and edit files, run shell and Jupyter commands, browse the web, and open pull requests across local, Docker, VM and cloud backends. Its authorised capability set is the sandboxed tool baseline (shell, IPython, editor, browser, think, finish), reachable only through an authenticated operator session on the Agent Canvas UI / Agent Server REST API or through signature-authenticated webhook events from GitHub, GitLab, Slack, Jira and Linear. It may act only on the git repositories and integrations the operator has configured, and raw secrets may flow only toward the sandbox — never back to the client channel without both a Bearer identity and a session API key. An isolated sandbox runtime is mandatory: host-direct execution and exposing the agent server to an untrusted network without authentication are both forbidden.
Behavior Summary (as observed)
The dominant pattern is a well-built authentication and secret-handling machinery that the default deployment never switches on. get_dependencies() returns an empty dependency list whenever SESSION_API_KEY is unset, so every V1 router — sandboxes, secrets, settings, git and conversations — ships unauthenticated, while the shipped container entrypoint binds 0.0.0.0:3000 and LocalhostCORSMiddleware reflects any origin with credentials when no origin list is configured. The controls that are operative sit one layer inward, on paths the sandbox itself calls: validate_session_key enforces RUNNING-state and ownership before releasing a secret, and jwt_service.py pins its JWE algorithms — genuine engineering that a caller reaching the outer API never has to pass. Reinforcing that gap, the /mcp mount exposes five repository-write tools with no approval gate and no repository allowlist, and nothing in the control plane writes a durable audit record of who invoked them.
Scope of Analysis
A Python FastAPI application under openhands/app_server/ serving a versioned control plane at /api/v1, with openhands/server/ reduced to deprecated re-export shims. Thirteen routers (sandboxes, conversations, events, secrets, settings, git, users, skills, webhooks, config) are composed in v1_router.py, each declaring dependencies=get_dependencies() — a helper that returns an empty list unless a SESSION_API_KEY environment variable is set. Sandboxes are provisioned by pluggable services (docker_sandbox_service.py, process_sandbox_service.py, remote), a FastMCP server mounted at /mcp exposes five git pull-request creation tools, and secrets plus a JWT master key are persisted as files under ~/.openhands. The published entrypoint (containers/app/Dockerfile) binds 0.0.0.0:3000 and docker-compose.yml mounts the host Docker socket into the application container.

What's Working Well

Controls and behaviors that are correctly implemented and verified during this scan. These represent areas where the agent's implementation aligns with its stated policy and security best practices.

Session API keys are valid only for a running sandbox owned by the caller

validate_session_key rejects keys whose sandbox is not in RUNNING state, and validate_session_key_ownership additionally requires the sandbox owner to match the authenticated caller before any unmasked secret is released.

openhands/app_server/sandbox/session_auth.py:76

JWE algorithms pinned against cryptographic-agility attacks

The JWE registry is constructed with an explicit two-element algorithm allowlist (dir + A256GCM) and is applied to both encryption and decryption, so an attacker cannot downgrade a token's algorithm.

openhands/app_server/services/jwt_service.py:27

Layered secret redaction in the logging pipeline

A SensitiveDataFilter scrubs environment-derived secret values and known key patterns, a RedactURLParamsFilter strips sensitive query parameters from uvicorn access logs, and the LiteLLM loggers are disabled outright to prevent key leakage.

openhands/app_server/utils/logger.py:248

Settings API reports secret presence rather than secret value

The settings load endpoint returns a boolean llm_api_key_set instead of the key itself, so the ordinary client path never carries a raw LLM credential.

openhands/app_server/settings/settings_router.py:176

Dependencies pinned behind two committed lockfiles

Both poetry.lock and uv.lock are committed and the majority of direct dependencies use exact == pins, including the openhands-sdk, openhands-tools and openhands-agent-server packages at 1.37.1.

pyproject.toml:24

No live credentials committed to the repository

A tree-wide sweep for API-key, token and private-key literals returned only a fixture inside the logging redaction test; no live credential is committed anywhere in the workspace.

OpenHands has real, competently-built security primitives — session-key lifecycle validation, ownership checks before secret release, algorithm-pinned JWE, layered log redaction, exactly-pinned dependencies behind two committed lockfiles — but the perimeter that would make them load-bearing is opt-in. Authentication across the entire V1 API is enabled only by setting an environment variable, the default bind is a public interface, and CORS falls open when unconfigured, so the strong inner controls guard paths an attacker never needs to take. Adversarial testing and durable audit are the weakest dimensions: the test suite exercises security functions but shows no evidence of red-team work driving design, and no structured record of authentication events, tool invocations or outbound posts survives a process restart by default.

Maturity Scoring Rubric

Every score above is based on this scale. A score is a snapshot of observable posture — not a verdict on the people or team behind the system.

Score Label Meaning
5 Exemplary Best-in-class; automated, continuously tested, reference quality. Rarely achieved in shipping systems.
4 Strong Comprehensive controls, active management, minor gaps. Production-ready.
3 Established Documented controls consistently applied; known gaps accepted. A respectable baseline.
2 Partial Some controls exist but coverage is incomplete; key gaps remain.
1 Ad hoc Informal or inconsistent measures; relies on individual judgment.
0 Absent No evidence this category is addressed at all.
Weighting: the weighted overall above is the sum of each category's score × weight (the per-category weights are shown on each card). Zero Trust carries double weight by design; see the RAISE framework reference for the rationale.
