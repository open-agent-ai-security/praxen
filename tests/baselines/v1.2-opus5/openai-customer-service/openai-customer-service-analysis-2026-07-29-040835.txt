BEHAVIOR SUMMARY
------------------------------------------------------------------------------
The dominant pattern is a framework that offers safe primitives and an agent
that uses none of them: the Agents SDK ships input and output guardrails,
per-tool needs_approval approval gates, and handoff input_filter, and
examples/customer_service/main.py constructs all three agents without a single
one. Every behavioral rule the remit treats as load-bearing — decline
off-topic and jailbreak requests, verify a confirmation number before changing
a seat, stop after a bounded number of failed attempts — exists only as
English inside a model instruction string, with no deterministic code path
that can enforce or halt. The sharpest instance is update_seat, which accepts
any model-supplied confirmation number, matches it against nothing, mutates
session state, and returns a success message even though no seat-management
backend exists. Working against that, the tool inventory is genuinely narrow
and structured tracing is correctly wired, so the agent is well-bounded in
what it *can* touch and well-instrumented in what it *did* — it is simply
ungoverned in between.

CRITICAL FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-29-001  update_seat applies a seat change against any
            model-supplied confirmation number, matching it to no booking
            record and passing through no approval gate.
      Action 1: In examples/customer_service/main.py, make update_seat look
                the supplied confirmation_number up in an authoritative
                booking record and return a refusal when it does not match the
                active session's booking, instead of assigning it to context
                at line 79.
      Action 2: Declare the tool as @function_tool(needs_approval=True) so the
                seat write suspends for explicit confirmation before it is
                applied.

  PRAX-2026-07-29-002  No input or output guardrail is wired on any of the
            three agents, so the remit's halt-and-decline escalation has no
            code path that can fire.
      Action 1: Add an @input_guardrail that trips on off-topic and jailbreak
                input and attach it to triage_agent in
                examples/customer_service/main.py, handling
                InputGuardrailTripwireTriggered in the run loop to emit an
                explicit refusal.
      Action 2: Add an @output_guardrail that blocks responses disclosing
                system instructions, so the no-system-prompt-disclosure rule
                has an enforcement point outside the model.

HIGH FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-29-003  Subject-matter scope lives only in prompt text, and the
            triage agent's instructions state no topic restriction at all.
      Action 1: State the airline-customer-service lane and an explicit
                decline behavior in triage_agent's instructions at
                examples/customer_service/main.py lines 126-129, rather than
                leaving scope implied by the handoff descriptions.
      Action 2: Back the prompt with the deterministic off-topic guardrail
                from PRAX-2026-07-29-002 so scope survives a jailbreak that
                rewrites the model's understanding of its role.

  PRAX-2026-07-29-004  Passenger name, confirmation number, flight and seat
            are exported unredacted to a hosted tracing backend that the remit
            never lists as a trusted service.
      Action 1: Pass a RunConfig(trace_include_sensitive_data=False) to
                Runner.run in examples/customer_service/main.py so passenger
                identifiers are excluded from exported spans while trace
                structure is retained.
      Action 2: Either add the tracing backend to the remit's Trusted Services
                list as an accepted processor, or register a local span
                processor so passenger data stays inside the operator's own
                systems.

  PRAX-2026-07-29-005  The session loop runs unbounded — the remit's
            max_failed_attempts cap appears nowhere in the codebase and no
            turn or cost ceiling exists.
      Action 1: Track failed confirmation-number and off-routine attempts in
                AirlineAgentContext and break the while True loop in
                examples/customer_service/main.py with an explicit decline
                once an operator-configured max_failed_attempts is reached.
      Action 2: Add a session-level turn or token ceiling alongside the
                inherited per-run max_turns, so an unbounded conversation
                cannot grow context and cost without limit.
