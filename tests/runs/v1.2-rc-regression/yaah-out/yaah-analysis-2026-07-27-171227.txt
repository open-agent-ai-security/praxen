BEHAVIOR SUMMARY
------------------------------------------------------------------------------
yaah is a genuinely security-oriented harness whose controls are real and
enforcing on its primary target — the command guard blocks catastrophic shell
commands before execution, the secret scanner blocks credential-bearing edits,
and a structured JSON session store durably records tool calls and blocked
commands — yet those protections are not delivered uniformly across the four
agents it configures. The dominant pattern is a uniformity gap: the generated
Codex configuration ships without the enforcing PreToolUse and PostToolUse
hooks (`hookmap.go` has no Codex mapping for either), so the command guard and
secret scanner degrade to advisory `yaah` MCP check-tools the model may simply
never call, and Codex sessions capture no tool-call audit trail. A second,
cross-cutting theme is that the control layer is itself unverified and its
trust boundaries partly under-pinned: the five protective handlers have no
tests at all, there is no threat model or security-disclosure process, and
while Go dependencies and remote skills are pinned, the `context7` and
`notion` MCP servers are fetched unpinned via `npx -y` on every run.

HIGH FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-27-001  Generated Codex configuration omits the enforcing
            PreToolUse and PostToolUse hooks, so the command guard and secret
            scanner are not delivered as hooks for Codex.
      Action 1: Deliver the PreToolUse command guard and PostToolUse
                secret/lint/comment checks to Codex — either by mapping
                Codex's available tool-call hook events in hookmap.go, or by
                making the yaah MCP check-tools a mandatory pre-execution step
                rather than advisory.
      Action 2: Ensure Codex sessions produce a tool-call audit trail
                equivalent to the Claude path so blocked commands and file
                modifications are recorded.

  PRAX-2026-07-27-002  Third-party MCP servers context7 and notion are fetched
            unpinned via `npx -y` on every run, with no version pin or
            integrity check.
      Action 1: Pin context7 and notion (and any npx-launched MCP server) to
                an exact published version, e.g. `@context7/mcp@`, and prefer
                an integrity-checked install path over `npx -y`.
      Action 2: Extend the supply-chain baseline check (doctor) to flag any
                MCP server launched via an unpinned package specifier.
