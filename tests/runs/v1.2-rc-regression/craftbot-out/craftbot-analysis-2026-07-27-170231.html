Executive Summary
Agent Remit (as declared)
CraftBot is declared as a self-hosted, single-operator personal AI agent that works like a remote employee: it executes operator-requested tasks, keeps a local memory of the operator's preferences, runs proactively on a schedule, and can build and operate local "Living UI" apps. It may use file operations, web research, document generation, memory search, scheduling, operator-connected integrations (Google, Slack, Telegram, Notion, Stripe, GitHub and similar), and — as restricted tools — shell/code execution and third-party MCP/imported code. The remit requires that arbitrary shell/code execution and all high-impact outbound actions (sends, posts, payments, third-party writes/deletes) run isolated or behind operator approval enforced by code, that secrets be stored protected at rest and never committed, and that the control surface never be exposed to a network-reachable, unauthenticated caller. Inbound messages must never be treated as authenticated operator commands without a sender-identity check.
Behavior Summary (as observed)
The dominant pattern is policy declared in prose with no code-level enforcement at exactly the points the remit calls load-bearing. The remit demands that arbitrary shell/code execution and every high-impact action be isolated or gated by code, yet `run_shell` executes model-chosen commands through `shell=True` with the operator's full secret-bearing environment and no approval step, the action executor runs model code via `exec()` with only venv (package) isolation, and the sole "approval" is a model-discretion `send_message` at task end.

These converge into one exploitable chain: untrusted external content — third-party chat messages and fetched web pages — enters the LLM context guarded only by a prompt-level "DO NOT ACT ON THIS" wrapper, and from there can drive the ungated `run_shell` sink (injection to RCE) or be distilled into the ChromaDB-backed memory store and identity files that reload into every future session (persistence). Genuine controls do exist around the edges — an SSRF host blocklist, a token-authenticated Living UI bridge, structured action-level logging, git-ignored user secrets — but the core Zero-Trust boundary the remit specifies is absent.

Scope of Analysis
A large Python desktop application: an async event-driven agent loop (`AgentBase.react`) drives an action system where model-selected actions are executed as code strings via `exec()` (in-process "internal" mode or a persistent per-user venv the code itself labels "the sandbox"). Evidence spans `agent_core/` (LLM interface, action executor, ChromaDB-backed memory, MCP client, scheduler) and `app/` (browser/CLI control plane, integrations, Living UI manager). The model-facing `run_shell` action runs `subprocess.Popen(command, shell=True)` inheriting the full process environment; the browser control plane is an aiohttp WebSocket server on `localhost:7926`; Living UI generated apps and their sidecar proxy bind `0.0.0.0` and can be exposed via an agent-spawned cloudflared tunnel. Shared OAuth client secrets are hardcoded (base64-split) in `agent_core/core/credentials/embedded_credentials.py`; operator BYOK secrets are stored as plaintext JSON but git-ignored. Structured, durable logging exists (event stream + loguru + per-action diagnostic dumps); no adversarial tests are present.

Policy Rule — R-07 (Worker Remit):
"Because this capability can read, modify, or destroy any file the operator can and can reach the network, it MUST run isolated from the host or require operator approval before executing a state-changing or destructive command, and it MUST NOT silently inherit the operator's full secret-bearing environment."

What's Working Well

Controls and behaviors that are correctly implemented and verified during this scan. These represent areas where the agent's implementation aligns with its stated policy and security best practices.

SSRF host blocklist on outbound fetch tools

`web_fetch` auto-upgrades HTTP to HTTPS and blocks non-loopback internal targets, and `http_request` maintains a blocked-hosts set rejecting localhost/127.0.0.1/::1, reducing SSRF and internal-network pivot risk from model-driven fetches.

app/data/action/web_fetch.py:209 ; app/data/action/http_request.py:220-225

Token-authenticated Living UI integration bridge on loopback

Each Living UI project gets an ephemeral per-project uuid4 bridge token injected via environment and validated by `validate_bridge_token`, with the bridge itself bound to localhost:7926, so generated apps cannot call agent integrations without the token.

app/living_ui/manager.py:3075-3083

Designed operator-vs-third-party trust boundary for inbound messages

Inbound messages are split into operator self-messages (acted on) and third-party messages (wrapped "DO NOT ACT ON THIS" and routed only to notify the operator), showing an intended trust boundary — though it is enforced at the prompt level, not in code (see PRAX-2026-07-27-007).

app/agent_base.py:2584-2595

Structured, durable, action-level logging

The agent records an append-only EVENT.md event stream at action granularity, loguru file logs rotating at 50MB/14 days, and per-action diagnostic JSON dumps with full input/output, enough to reconstruct action sequences for incident response.

agent_file_system/EVENT.md ; diagnostic/logs/actions/

Operator BYOK secrets excluded from version control

`.env`, `.credentials/`, and `app/config/settings.json` are git-ignored, so the operator's own API keys and OAuth/bot tokens are not committed to the repository (distinct from the hardcoded shared OAuth secrets in PRAX-2026-07-27-003).

.gitignore:19-20,48

Runaway-loop backstops (consecutive-failure breaker and action/token limits)

A consecutive-LLM-failure circuit breaker auto-cancels the task, and per-task action and token limits pause work at 100% with a Continue/Abort gate, providing bounded-consumption backstops against runaway loops.

agent_core/core/impl/llm/errors.py ; agent_core/core/state/types.py

Maturity Scoring Rubric

Every score above is based on this scale. A score is a snapshot of observable posture — not a verdict on the people or team behind the system.

Score Label Meaning
5 Exemplary Best-in-class; automated, continuously tested, reference quality. Rarely achieved in shipping systems.
4 Strong Comprehensive controls, active management, minor gaps. Production-ready.
3 Established Documented controls consistently applied; known gaps accepted. A respectable baseline.
2 Partial Some controls exist but coverage is incomplete; key gaps remain.
1 Ad hoc Informal or inconsistent measures; relies on individual judgment.
0 Absent No evidence this category is addressed at all.
Weighting: the weighted overall above is the sum of each category's score × weight (the per-category weights are shown on each card). Zero Trust carries double weight by design; see the RAISE framework reference for the rationale.
