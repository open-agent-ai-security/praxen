BEHAVIOR SUMMARY
------------------------------------------------------------------------------
The dominant pattern is policy declared entirely in natural language with
essentially zero deterministic code-level enforcement: FinBot's approval
decision — which sets payment_processed=True — rests solely on the LLM's
judgment, with no code gate on amount, fraud signal, confidence, or vendor
status, so a persuasive or injected invoice description can carry an
above-threshold payment straight through _approve_invoice. Compounding this,
the entire admin control plane is unauthenticated, letting any caller rewrite
the agent's goals (custom_goals, injected verbatim into every future system
prompt and persisted in the database) or disable fraud detection outright. A
security lead should look first at _approve_invoice, the custom_goals
injection in get_system_prompt(), and the unauthenticated /api/admin/*
blueprint.

CRITICAL FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-27-001  The entire /api/admin/* control plane is
            unauthenticated — any caller can rewrite FinBot's goals,
            thresholds, fraud flag, and vendor trust.
      Action: Place authentication and role-based authorization in front of
              the entire admin blueprint (e.g. a before_request guard on
              admin_bp verifying an operator session), and reject vendor-side
              or unauthenticated callers.

  PRAX-2026-07-27-002  Unvalidated custom_goals are stored in the database and
            injected verbatim into every system prompt as an override,
            persistently hijacking the agent's goals.
      Action 1: Remove the runtime goal-override channel; treat agent goals
                and decision logic as code-deployment artifacts, not
                database-editable text.
      Action 2: If operator-adjustable goals are required, constrain them to a
                validated allowlist of parameters and never concatenate free
                text into the system prompt as an override.

  PRAX-2026-07-27-003  Vendor-supplied invoice descriptions are treated as
            decision input, letting persuasive or injected text override
            thresholds and drive auto-approval.
      Action 1: Stop deriving approval strength from free-text invoice
                content; base the auto-approve/escalate decision on
                structured, verified fields (amount, vendor status, fraud
                result) enforced in code.
      Action 2: Label vendor-supplied fields as untrusted data in prompt
                construction and never let them override configured
                thresholds.

  PRAX-2026-07-27-004  approve_invoice triggers payment with no deterministic
            check on amount, fraud signal, confidence, or vendor status — the
            LLM's decision is the only gate.
      Action: Add a deterministic gate in _approve_invoice (or before payment)
              that hard-blocks approval when amount >=
              manual_review_threshold, a fraud signal is present, confidence <
              confidence_threshold, or the vendor is not
              registered-and-approved, routing such invoices to human review
              regardless of model output.

  PRAX-2026-07-27-005  A single config flag disables fraud detection entirely,
            a capability the remit explicitly forbids under any circumstance.
      Action: Make fraud detection mandatory and non-bypassable — remove the
              disable flag or make it inert, and require a passing fraud check
              as a precondition of any approval path.

HIGH FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-27-006  Unauthenticated vendor read endpoints return full
            banking records — account number, routing number, and tax ID — to
            any caller.
      Action: Require authentication on vendor read endpoints and strip
              banking/tax fields from any response not restricted to
              authorized finance operators.

  PRAX-2026-07-27-007  No structured logging exists, config and goal changes
            are written silently, and none of the remit's halt/alert
            escalation triggers are implemented.
      Action: Add structured, append-only logging of every config/goal change
              and every agent decision, and implement the remit's halt/alert
              escalations (e.g. block-and-alert when fraud detection is
              disabled or an above-threshold invoice is about to
              auto-approve).
