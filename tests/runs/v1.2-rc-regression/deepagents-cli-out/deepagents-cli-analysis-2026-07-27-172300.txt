BEHAVIOR SUMMARY
------------------------------------------------------------------------------
This is a mature, security-conscious deterministic CLI whose declared
boundaries are largely enforced in code: HTTPS-with-no-userinfo transport
(`api_client._normalize_endpoint`, `trust_env=False`), project-`.env` blocking
of endpoint/proxy/TLS overrides, symlink and path-escape rejection during
bundle assembly (`project._ensure_project_contained`), confirmation gates on
remote-mutating and destructive actions, and MCP auth-header redaction. The
dominant pattern is *declared-transport-security enforced for the platform
endpoint but not re-applied to referenced MCP-server URLs*: neither
`mcp-servers add` nor `deploy` validates that a remote MCP URL uses TLS, so
the remit's "MUST use TLS" rule for MCP servers is unenforced (and, tellingly,
untested) while the analogous platform-endpoint rule is both enforced and
tested. The remaining findings are posture gaps rather than exploitable chains
— two dependencies lack upper version bounds, the shipped threat model no
longer matches the shipped code, and the documented `--header
X-Api-Key=$SECRET` workflow places credentials on the command line.

HIGH FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-27-001  Neither `mcp-servers add` nor `deploy` validates that a
            referenced remote MCP server URL uses TLS, so `http://`/`ws://`
            servers are registered and deployed unchecked.
      Action 1: In `commands._execute_mcp_server_add` (and
                `_execute_mcp_server_update`), reject any `--url` whose scheme
                is not `https`/`wss` before calling `create_mcp_server`.
      Action 2: In `mcp_resolver.resolve_referenced_servers` (or
                `project._read_tools_json`), fail the deploy when any
                referenced `mcp_server_url` is not TLS, so a
                previously-registered non-TLS server cannot ride through.
